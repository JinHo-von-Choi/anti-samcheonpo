# 제한된 복구와 전달 근거 v1

복구 정책은 코드를 실행하거나 모델·권한·외부 연결을 바꾸지 않는다. 감지된 원인에 맞춘 다음 행동 하나와 종료 조건을 전달한다. 권한·명령 부재·네트워크 장애는 실패한 실행의 오류 문구가 있을 때 환경 문제 후보로 분류하며, 모델 교체나 추측성 코드 수정으로 해결됐다고 가정하지 않는다.

## 반복 한도

같은 목표 개정에서 원인별 처방은 1회, 전체 제안은 최대 3회다. 한 제안의 전달·관찰이 미확인인 동안 새 처방을 연속 생성하지 않는다. 이후 같은 원인이 다시 나타나면 한 번의 인수인계만 제안하며 인수인계 자체도 반복하지 않는다. 제안 단계에서 예산을 예약하므로 지원되지 않는 출력·느린 클라이언트를 이유로 무한 재전송하지 않는다. 명시적인 계약 개정은 이전 대기 처방을 폐기한다.

기존 명시적 예산·보호 경로·종료 차단 규칙을 이 정책이 해제하지 않는다. 복구 권고가 지원된다고 차단도 지원된다고 취급하지 않는다. 어댑터 능력에 따라 에이전트 문맥 주입, 사용자 메시지, 관찰 전용 중 하나를 선택한다. 관측 사실만 보내는 비교군에는 처방을 보냈다고 기록하지 않는다.

## 기록 단계

- `proposed`: 다음 행동을 정해 대기열에 넣음. 전달 시각은 없다.
- `emitted`: 지원 능력 필터와 방언 변환을 통과한 메시지를 소켓에 기록함.
- `delivered`: 같은 연결의 일회용 토큰으로 훅 클라이언트의 stdout 쓰기 완료를 확인함. 에이전트가 읽음·동의함·수행함의 증거는 아니다.
- `acknowledged`: 전달 뒤 명시적인 keep/steer 인터페이스 명령을 받음. 사람의 신원이나 실제 실행을 증명하지 않는다.
- `effect_observed`: 전달 이후 10개 이벤트 관찰창에서 같은 규칙의 재발 여부를 기록함. `no_recurrence_observed`는 해결 또는 개입의 인과 효과를 뜻하지 않는다.
- `censored`: 전달 미확인, 지원 불가, 종료·재시작·목표 변경 등으로 충분한 관찰을 얻지 못함.

관찰창은 제안 시점이 아닌 전달 시점의 이벤트 경계에서 시작한다. 출력 실패·잘못된 토큰·구형 클라이언트의 확인 부재는 전달 성공으로 바꾸지 않는다. 클라이언트는 확인 응답을 기다리지 않으며, 서버는 확인을 짧게만 기다린다. 복구 메시지가 없는 평상시 훅에는 이 교환을 추가하지 않는다.

## 집계

`samcheonpo eval --interventions`의 개입 실험 표는 결과를 관측 상태별로 따로 센다: 재발 미관측(`no_recurrence_observed`), 재발(`recurrence_observed`), 전달 미확인(`delivery_unconfirmed`, `unsupported_delivery`), 중단(그 밖의 censored 사유), 진행 중(아직 관찰창이 닫히지 않음), 이전 버전이 쓴 `resolved`(JSON의 `legacy_unknown`, 표에서는 중단 열에 합산). 재발 미관측 비율의 분모는 관찰창이 닫힌 전달 확인 건수다. 어느 상태도 "해결"로 합치지 않는다.

migration 0004는 과거 intervention 행을 `legacy_unknown`으로 보존한다. 새 행의 `delivered_at`은 수신 확인 전까지 NULL이다. 원인·처방·종료 조건·선택된 전달 경로·관찰 상태는 `recovery_attempt`에 보존하고 인수인계에서 읽는다. 전달 시각과 관찰 경계는 이후 덮어쓰거나 뒤로 되돌릴 수 없다.

같은 OS 사용자는 훅 출력과 원장을 조작할 수 있다. 이 기록은 기능의 전달 단계를 구분하는 증거이며, 악의적인 동일 계정 프로세스에 대한 인증이나 격리 장치는 아니다. 별도 사용자 연구와 비교 실험 없이 복구 성공률을 홍보하지 않는다.
