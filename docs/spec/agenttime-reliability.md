# 대기 반복·진행 정체 안내

작업이 끝났는데 계속 기다리거나, 수정해도 같은 검사에서 실패가 이어지는지 살펴본다. 이런 행동이 이어지면 확인한 근거와 다음에 검토할 일을 알려 준다.

기본적으로는 기록만 남긴다. 사용자가 안내를 켜면 가벼운 안내를 제공한다. 두 규칙으로 작업을 차단하는 일은 없다. 사용자가 정한 비용·시간·토큰 상한과 보호 경로는 기존 규칙대로 지킨다.

안내는 추정이다. 완료 여부를 확인할 자료가 부족하거나 기다리는 이유를 알 수 없으면 판단을 보류한다.

## 안내 켜기

사용자 설정 파일 `~/.samcheonpo/config.yml`에 아래 내용을 넣는다. 기존 설정이 있으면 해당 항목에 합친다.

```yaml
rollout:
  mode: recommend
  recommend_rules: [s1.explicit_waiting, s8.progress_stall]
```

두 이름은 각각 **대기 반복**과 **진행 정체** 규칙이다. 원하는 것 하나만 넣어도 된다.

- `shadow`는 기록만 남기는 상태다. `mode: shadow`이면 위 목록에 넣어도 안내하지 않는다.
- `recommend_rules`는 사용자가 안내를 받기로 선택한 목록이다. 프로젝트의 `.samcheonpo.yml`에서는 이 권한을 추가할 수 없다.
- `shadow_rules`는 계속 기록만 할 규칙의 목록이다. 기존 설정에 이 목록을 적었다면 안내하려는 규칙을 그 목록에서도 빼야 한다. 프로젝트가 목록에 추가한 규칙도 계속 기록만 한다.

설정의 `L1`은 가벼운 안내 수준을 뜻한다. 두 규칙은 이 수준까지만 안내한다. 평가 자료를 등록하는 `validated` 단계에서도 차단으로 바뀌지 않는다.

## 언제 안내하나

### 완료 뒤 대기 반복

예를 들어 현재 입력으로 모든 완료 검사를 통과했고 더 지켜봐야 할 조건도 없는데, 다른 작업과 연결되지 않은 `sleep` 실행이 세 번 이어지면 안내 후보가 된다. 불필요한 대기인지는 추정으로 표시한다.

다음 조건을 모두 확인해야 한다.

- 사용자가 계약과 시간 조건을 수락했다.
- 모든 완료 검사의 통과 근거가 현재 목표·입력·환경에서도 유효하다.
- 필요한 관찰 기간이나 종료 조건을 충족했다.
- 대기 호출이 정상 종료됐고, 연결된 작업을 기다리는 호출이 아니다.

현재 자동으로 해석하는 것은 단독 `sleep` 명령뿐이다. 명령을 이어 붙인 경우, 코드 안의 타이머, 시계 조회는 이 근거로 쓰지 않는다.

끝나지 않은 백그라운드 작업이 있거나 대기 이유를 알 수 없으면 안내를 보류한다. 사람이 확인해야 하는 완료 조건이 포함된 계약도 대기 안내를 보류한다. 현재는 그 확인을 저장하고 검증하는 기능이 없기 때문이다.

### 수정해도 개선되지 않는 검사

같은 완료 검사에서 입력을 바꿔 다시 시도했지만 실패가 줄지 않으면 진행 정체를 살펴본다. 기본 기준은 다음 세 가지를 모두 만족하는 것이다.

- 비교 가능한 실패가 3회 이상이다.
- 그 구간에서 도구 실행을 5회 이상 관측했다.
- 검사 입력이 실제로 바뀌었다.

검사 명령과 실행 환경이 같아야 결과를 비교할 수 있다. 실시간 판단에는 삼천포가 직접 실행한 **체크포인트 검사**를 쓴다. 이 검사는 v2 계약의 `pure`·`reuse` 설정으로 입력과 환경을 확인해야 한다.

같은 검사가 통과하거나, 완전한 결과에서 실패 목록이 줄면 정체 기록을 초기화한다. 다른 검사의 통과나 일반 명령의 성공만으로는 해당 검사에 개선이 있었다고 볼 수 없다.

결과가 잘렸거나 실패 목록이 빠진 경우, 실행마다 결과가 달라지는 불안정한 검사(flaky), 환경 변경, 조사 작업, 아직 필요한 관찰을 진행 중인 경우에는 판단을 보류한다. 입력이 같은 재실행은 기존 반복 검사·실패 규칙(S1·S2)이 처리한다.

파일 감시에 오류가 있거나 도구 기록이 누락된 경우에도 두 규칙의 안내를 보류한다.

## 얼마나 지켜봐야 하는지 정하기

v1·v2 계약 파일 `.samcheonpo/contract.yml`의 `temporal_requirement`에 시간 조건을 적는다. 아래 예시는 완료 검사를 충족한 뒤에는 추가 관찰이 필요 없다는 뜻이다.

```yaml
temporal_requirement:
  kind: completion
```

| 종류 | 뜻 | 함께 적을 값 |
| --- | --- | --- |
| `completion` | 완료 조건을 충족하면 추가 관찰 없이 끝낼 수 있음 | 없음 |
| `minimum_duration` | 정해진 시간 동안 계속 관찰해야 함 | 양수 `seconds` |
| `observe_until` | 지정한 완료 검사가 확인될 때까지 관찰해야 함 | `done`에 있는 검사의 `check_id` |

예를 들어 최소 60초 관찰 조건은 다음과 같다.

```yaml
temporal_requirement:
  kind: minimum_duration
  seconds: 60
```

이 필드를 생략하면 필요한 관찰 조건을 알 수 없으므로 대기 안내를 보류한다. 조건을 바꾸면 사용자가 다시 수락해야 한다.

최소 관찰 시간은 삼천포가 연속으로 관찰한 시간으로 잰다. 재시작하면 새 관찰 구간을 시작한다. 모델의 시간 보고나 기존 활동 시간 값(`mar.active`)은 이 조건의 충족 근거로 쓰지 않는다.

시간 조건은 예산을 늘리지 않는다. 예를 들어 최소 60분 관찰과 30분 상한을 함께 정하면 목표 카드에 충돌을 표시하고 대기 판단을 보류한다.

## 개발자용: 설정과 기록

### 판단 기준 조정

아래 값은 기본 최소 기준이다. 기준을 높이면 더 많은 반복을 관측한 뒤 안내한다.

```yaml
detectors:
  s1_verify_treadmill:
    explicit_waiting_repeats: 3
  s8_cost:
    stall_failures: 3
    stall_tool_events: 5
```

이전 사용자 설정에 새 규칙 이름이 없더라도 자동으로 안내를 켜지 않는다. 사용자가 `recommend_rules`에 선택한 규칙만 안내 대상이 된다. `shadow_rules`를 직접 적지 않았다면 선택한 규칙만 기본 기록 전용 목록에서 빠진다.

`s1.verify_after_docs`와 `s1.review_repeat`의 기본 기록 전용 상태는 이 선택으로 바뀌지 않는다. `escalate_max_blocks`와 `validated_rules`를 바꿔도 대기·정체 두 규칙의 차단 권한은 생기지 않는다.

### 목표 변경과 재시작

이벤트의 선택 필드 `reliability`에 작업 ID(task), 목표 개정(revision), 수락한 계약의 해시(authority hash), 입력·환경 해시와 관측 상태를 저장한다. 계약 해시는 어떤 조건을 수락했는지 구분하는 값이다. 시간 조건도 이 값에 포함된다.

이 값은 호출을 시작할 때 고정한다. 뒤늦게 도착한 결과를 새 목표의 근거로 쓰지 않는다. 새 문맥에는 명령·출력·패치·환경변수 원문을 추가 저장하지 않는다.

대기 방식(`wait_kind`)과 다른 작업을 기다리는 관계(`wait`)는 따로 기록한다. 구조화한 외부 기록에서도 관계를 확인하지 못하면 미상(`unknown`)으로 남긴다. 관찰 상태의 `none`은 추가 관찰이 필요 없다는 뜻이고, `fulfilled`는 선언한 관찰 조건을 충족했다는 뜻이다. `pending`은 관찰 중, `unknown`은 확인할 수 없음을 뜻한다.

최근 근거는 128개, 판단 대상은 64개까지 보관한다. 한도를 넘으면 오래된 후보를 버리고 퇴출·판단 보류 통계를 남긴다. 저장 용량 때문에 후보를 버린 일과 실제 도구 기록이 누락된 일은 구분한다. 파일 감시 오류나 감시 한도 초과는 관측 불완전으로 기록한다. 커널 감시 한도는 자동으로 바꾸지 않는다.

재시작하면 저장한 구조화 사실로 후보를 다시 만든다. 과거 구간에 새 알림이나 비용을 만들지 않는다. 저장된 판정과 같은 대상에 대한 반복 안내 억제 기간(쿨다운)은 유지한다. 복원에 필요한 자료가 없는 이전 기록은 미상으로 남긴다. 새 체크포인트 사실은 기존 S1·S2 카운터에 넣지 않는다.

대기·정체 추정만으로 이벤트에 낭비 금액이나 토큰을 추가 배정하지 않는다. 비용 표시는 [영수증 규격](receipt-billing.md)을 따른다.

## 격리 코퍼스 평가

코퍼스는 평가에 사용할 기록 모음이다. 저장된 기록을 다시 분석해 탐지 결과를 확인하고, 사람이 따로 붙인 정답 라벨과 비교할 수 있다.

저장소 루트에서 다음 명령으로 제공된 6개 합성 사례를 확인한다.

```sh
go run ./cmd/samcheonpo eval corpus \
  --manifest internal/eval/testdata/agenttime/manifest.json \
  --labels internal/eval/testdata/agenttime/labels.json \
  --set eval --out /tmp/samcheonpo-corpus-report.json
```

사용자 설정·원장은 열지 않는다. 기록에 들어 있는 명령도 실행하지 않는다. 분석은 임시 작업 폴더에서 진행하며 전역 `--db` 옵션도 사용하지 않는다.

| 옵션 | 용도 | 생략했을 때 |
| --- | --- | --- |
| `--manifest` | 평가할 원본과 분할을 적은 파일 | 필수 |
| `--labels` | 별도로 준비한 정답 라벨 | 탐지·적용률만 보고, 채점하지 않음 |
| `--set train\|eval` | 조정용(train) 또는 평가용(eval) 분할 선택 | eval |
| `--out` | JSON 보고서 경로 | 표준 출력 |

출력 파일의 상위 폴더는 미리 만들어야 한다. 제공된 합성 사례는 기능이 깨지지 않았는지 확인하는 시험이다. 실제 AgentTime에서의 탐지 성능이나 비용 절감 효과는 별도 평가가 필요하다.

### 원본과 과제 분할

Manifest는 평가 입력 목록이다. `version`에는 `reliability-corpus/1`, `cohort`에는 기록 모음 이름을 적는다. `runs` 배열의 각 실행 기록(run)에 아래 값을 넣는다. 파일 경로는 manifest 위치를 기준으로 읽는다.

| 필드 | 뜻 |
| --- | --- |
| `id`, `benchmark`, `task_raw_id` | 실행 기록, 벤치마크, 원본 과제 식별자 |
| `split` | train 또는 eval |
| `path`, `format` | 원본 경로와 claude/codex/normalized 형식 |
| `sha256` | 원본 내용이 바뀌지 않았는지 확인할 해시 |
| `session_id` | 원본 세션 ID가 run ID와 다를 때 지정 |

같은 `benchmark + task_raw_id` 과제와 같은 원본 해시를 train·eval 양쪽에 넣을 수 없다. 과제나 기록을 조정과 평가에 중복 사용하지 않도록 검사한다.

평가할 계약은 `contract_path`, `contract_sha256`, `provenance`로 미리 고정한다. `provenance`에는 자료를 준비한 출처를 적는다. 원본에 관측 문맥이 없으면 `context_path`, `context_sha256` 파일의 `events`에 원본 이벤트 번호(Seq)별 `reliability` 값을 제공한다. 존재하지 않는 이벤트 번호는 거부한다. 문맥은 정답 라벨을 읽기 전에 고정하며, 모델 자기 보고나 정답을 복사해 만들지 않는다.

AgentTime 기록 모음에는 공개 배포 자료의 경로(`metadata_path`), 해시(`metadata_sha256`), 포함 조건(`filters`)이 필요하다. 공개 레코드의 `id`로 연결하고 `benchmark`, `task_raw_id`가 일치하는지 검사한다. 원본 배포 자료·manifest·선택 분할·파싱 제외 수는 따로 보고한다. `in_default`만으로 논문의 주 평가 집합을 재현했다고 보지 않는다.

### 정답 라벨

라벨 파일은 같은 버전, 라벨 작성자(`labeler`), `labels` 배열을 가진다. 각 라벨에는 `run_id`, 규칙 이름(`rule`), 해당 규칙의 양성 여부(`positive`)를 적는다. 원시 대기 사실의 존재 여부는 선택 필드 `raw_wait`로 적는다.

모든 탐지 결과를 먼저 확정한 뒤 라벨을 읽는다. 라벨이 없는 기록은 채점에서 제외하고, 음성으로 바꾸지 않는다.

### 보고서 읽기

채점 단위는 실행 기록 한 건에서 해당 패턴이 나타났는지 여부다.

| 결과 | 의미 |
| --- | --- |
| 원시 대기 사실 | 실제 대기 호출을 추출했는지 |
| `detected_runs` | 규칙의 안내 조건을 만족한 기록 수 |
| `deliverable_runs` | 출시 설정·쿨다운·실험군까지 반영해 전달할 수 있는 후보 수 |
| 적용 가능·비대상·미상 | 판단 조건을 갖췄는지, 대상이 아닌지, 확인할 수 없는지 |
| 퇴출·보류 | 용량 제한으로 버린 후보와 판단을 보류한 관측 수 |

전달 후보 수만으로 실제 훅 출력이나 사용자의 대응을 확인할 수는 없다. 보고서는 전체·적용 가능 기록을 나눠 정밀도(precision), 재현율(recall), 오탐률(FPR)과 Wilson 신뢰구간을 제공한다. 분모가 0이면 비율은 `null`이다. 파싱에 실패한 원본도 제외 사유와 함께 남긴다.

현재 판정기 버전은 `samcheonpo-eval/0.3.1`이다. 보고서에는 manifest·라벨·설정 해시와 단가표 버전을 함께 기록한다. `effectiveness_validated`는 `false`로 남는다. 이 명령은 제품 효과를 자동 인증하지 않는다.

### 전달 설정을 가정해서 평가하기

Manifest의 `evaluation_rollout`으로 안내 설정을 가정할 수 있다. 아래 항목을 기존 manifest에 합치면 두 규칙의 안내 전달 후보를 평가한다. 사용자 설정은 바뀌지 않는다.

```json
{
  "evaluation_rollout": {
    "mode": "recommend",
    "shadow_rules": ["s1.verify_after_docs", "s1.review_repeat"],
    "experiment_enabled": false
  }
}
```

생략하면 제품 기본값처럼 기록만 한다. `experiment_enabled`를 켜면 결정적으로 배정한 실험군에 따라 일부 안내를 보류한다. 탐지 결과는 보존한다.

## 확인한 범위와 남은 검증

v0.6.0에 포함했으며 2026-10-10 로컬 시험을 수행했다. 실제 에이전트에서의 새 안내 전달은 아직 확인하지 않았다.

| 확인 항목 | 결과 |
| --- | --- |
| 전체 Go 시험·관련 race 검사·vet | 통과. 아래 두 통합 시험은 환경 문제로 건너뜀 |
| 적합성 검사 | 20건 통과 |
| 합성 기록 평가 | 6건, 파싱 제외 0, 두 규칙 각각 양성 1건 탐지 |
| 기본 설정의 전달 후보 | 0건 — 기록만 하는 설정 |
| 훅 처리 | 200회 정상 응답, 시간 초과·실패·큐 누락 0 |
| 훅 처리 시간 | p95 2.53ms, 기준 6ms. 요청 95%가 이 시간 안에 처리됨 |

호스트의 파일 감시 자원이 고갈돼(inotify `ENOSPC`) 마지막 통합·live race 검사에서 `TestWatchInvalidates`, `TestAgentTimeLiveShadowAndInputInvalidation`을 건너뛰었다. 감시 실패·용량 초과 때 판단을 보류하는 동작은 별도 시험으로 확인했다. 커널 설정은 변경하지 않았다.

남은 검증은 실제 AgentTime 원본과 독립 라벨을 이용한 성능 평가, 그리고 안내를 켠 경우와 끈 경우의 완료율·비용·오탐 비교다. 이 비교 실행이 프로젝트의 G12 효과 검증 관문이다. 플랫폼별 확인 수준은 [지원 범위](../support-matrix.md)를 따른다.
