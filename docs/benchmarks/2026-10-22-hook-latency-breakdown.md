# 훅 지연 구간 분해와 Rust 전환 결정

작성일: 2026-10-22
대상: `docs/plans/2026-10-22-hybrid-rust-hook-and-governor-enhancement-plan.md` 작업 0
환경: Linux 6.8.0-138-generic x86-64, 72코어, load average 44.6~47.4, Go 1.27.1, Rust 1.97.1(cargo 1.97.1)

## 1. 왜 다시 쪼갠다

원안은 "현행 p95 9.29ms → 2.50ms"를 전제로 했다. 저장소 안에서 9.29는 없고, 실제 기록은 두 개다. `GATES.md`(2026-10-21, 600회)의 **처리 구간 p95 2.50ms**와 **프로세스 기동 포함 p95 9.16ms**. 두 값은 같은 분포가 아니며, `docs/spec/hook-startup.md`는 두 구간을 더해서 전체 지연으로 해석하지 말라고 못박는다.

더 중요한 것은 처리 구간 2.50ms가 이미 **데몬 왕복을 포함**한다는 점이다. `internal/hookclient/hookclient.go`의 `handling_ns`는 stdin을 읽기 전에 시작하고 응답을 출력한 뒤에 끝난다. 데몬을 Go로 두면 이 구간은 줄지 않는다. 줄일 수 있는 것은 프로세스 기동 구간뿐이다.

이번 문서는 그 구간을 실제로 쪼개고, 계획에 미리 적어 둔 결정 규칙을 적용한다.

## 2. 측정 방법

- 부모측정(exec 시작 ~ 자식 종료). 저장소 게이트(`scripts/check-hook-budget.sh` → `samcheonpo bench-hook`)와 같은 방식이라 게이트 출력과 나란히 비교할 수 있다.
- 측정기는 `/tmp/latency/latency`(std만 사용). 매 실행은 `exec.CommandContext` + 파이프 + 대기이며, 게이트와 같은 구조다.
- 각 측정 600회. 데몬 세션은 워밍업 50회를 버리고 600회를 기록했다.
- 격리: 데몬 세션은 임시 홈(`SAMCHEONPO_HOME`)을 따로 만들고 그 경로의 소켓만 사용했다. 전송만 측정하는 구간은 **데몬을 한 번도 띄우지 않은** 별도 홈에 즉시 응답하는 에코 서버를 세웠다.
- 세그먼트 정의:
  - (a) 프로세스 기동·종료: 훅을 입출력 없이 실행(Go 훅은 인자가 없으면 즉시 종료, Rust 프로토타입은 즉시 종료).
  - (b) 전송 왕복: 에코 서버(즉시 `{"output":null}`)를 상대로 한 왕복의 처리 구간.
  - (c) 데몬 판정: 실제 데몬을 상대로 한 왕복의 처리 구간에서 (b)를 뺀 값.

전송만 에코 서버는 즉답하지만 판정은 하지 않는다. 실제 데몬은 같은 데몬에 Go 훅과 Rust 프로토타입을 번갈아 붙여 측정했다(C1 → C2 → C3).

## 4. 결정

계획이 미리 정한 규칙을 그대로 적용한다.

> Go의 (a)가 4ms 이상이면 Rust가 6.66ms 구간에서 줄일 수 있는 몫이 커서 Rust 채택 근거가 된다. E2E 목표는 실측 (a) 감소량 + 2.50ms 처리 구간 + 관측 오차로 정한다.
> Go의 (a)가 1.5ms 이하이면 9.16ms의 대부분은 데몬·스케줄러 부하이고 Rust 전환의 이득이 작다. 이 경우 전송 언어 변경을 보류하고 데몬 쪽 병목을 먼저 줄인다.

Go (a) p95 = 6.436ms. 규칙상 **Rust 채택**이다.

**확정 목표**

| 지표 | 목표 | 근거 |
| --- | --- | --- |
| E2E p95(프로세스 기동 포함) | **≤ 5.00ms** | Rust (a) 2.266ms + 처리 구간 2.50ms + 여유 약 0.3ms. 실측 C2 3.445ms가 기준점 |
| 처리 구간 p95 | **≤ 2.60ms 유지** | 현행 게이트 기준. Rust 전환이 늘리면 실패 |
| 빠른 실패·수신 누락·타임아웃 | 0 | 응답 600/600, 타임아웃 0, 실패 0, 도구 수신 600/600, 큐 누락 0 |
| Rust 바이너리 크기 | ≤ 500KB | 실측 288,216B(의존성 없음) / 349,520B(serde 포함) |

원안의 "E2E p95 2.50ms"는 기동 하한(1.8ms)과 실측 데몬 왕복을 더하면 이미 넘으므로 폐기한다.

## 5. 바이너리 크기

2026-10-22 이 호스트 실측이다.

| 바이너리 | 크기 |
| --- | --- |
| Go 훅 (`CGO_ENABLED=0 -trimpath -ldflags "-s -w"`) | 3,502,240 B |
| Go CLI (같은 플래그) | 33,599,648 B |
| Rust, 의존성 없음(`-O -C panic=abort -C strip=symbols`) | 348,728 B |
| Rust + serde/serde_json(`opt-level="z" lto strip`) | 288,216 B |
| Rust 프로토타입(Cargo.toml 그대로) | 349,520 B |

원안의 "5.2MB"는 이 호스트에서 재현되지 않았다. Go 훅의 strip 전 크기는 5.2MB에 가깝지만, 배포본은 strip 된다. **릴리스 파이프라인의 실제 크기(릴리스 스크립트는 `-s -w`를 쓴다)를 기준으로 한다.**

## 6. 확인하지 못한 것

- **호스트·부하 의존성.** 이 수치는 72코어·load average 45~47인 한 호스트의 관측값이다. GATES.md가 기록한 macOS 러너의 느린 기동 45.69ms 같은 변동은 이 측정 밖이다. CI 러너에서 같은 결론이 재현되는지는 러스트 훅이 붙은 뒤 다시 확인한다.
- **Rust 프로토타입과 완성 구현의 차이.** 프로토타입은 소켓 경로 결정, 응답 스키마 검증, 전달 확인 회신, 데몬 기동을 하지 않는다. 완성 구현은 프로세스당 시간이 더 든다. 목표를 3.445ms가 아니라 5.00ms로 둔 이유다.
- **Windows·macOS.** Windows에서 Rust 표준 라이브러리의 UDS 지원 여부와 macOS 경로 규칙 일치는 이 호스트에서 확인하지 않았다.
- **데몬 판정 1.9ms의 분해.** 데몬 안에서 판정이 어디에 쓰이는지는 나누지 않았다. 데몬 병목은 Rust 전환과 별개 작업이다.
- **Go 훅 이진수의 E2E가 C1(8.298ms)과 C3(8.036ms) 사이에서 3% 흔들린다.** 같은 데몬·같은 워밍업인데도 세션 상태에 따라 달라진다. 단일 측정값이 아니라 반복으로 읽어야 한다.
